Your infrastructure has natural hierarchies: flakes contain configurations, configurations contain machines. Panix's configuration model reflects this:

<center>
**Fleet → Flake → Configuration → Machine**
</center>

Attributes at each level cascade down, **without overriding** child attributes. Slices (tags, secrets, disk encryption keys) **append**. Define once at the fleet, extend at any level:

```yaml
fleet:
  tags: [production]              # Inherited by all descendants
  secrets:                        # Inherited by all descendants
    - local_path: ./secrets/common.key
      remote_path: /var/secrets/common.key
  
  flakes:
    infrastructure:
      tags: [critical]            # Accumulated: [production, critical]
      secrets:                    # APPENDED to inherited secrets
        - local_path: ./secrets/prod/api.key
          remote_path: /var/secrets/api.key
      
      configurations:
        webserver:
          tags: [web]             # Accumulated: [production, critical, web]
          
          machines:
            web-01:               # Accumulated: [production, critical, web, web-01]
            web-02:
              secrets:            # APPENDED to all inherited secrets
                - local_path: ./secrets/web-02/cert.pem
                  remote_path: /etc/ssl/cert.pem
```

## Why Configurations Are Separate From Machines

In NixOS, a `nixosConfiguration` defines a system: packages, services, filesystem layout.

Traditional deployment tools assume a 1:1 mapping: one machine, one `nixosConfiguration`. Deploying 50 identical machines would require 50 `nixosConfiguration` entries and 50 builds, even though the systems are identical.

Panix breaks this 1:1 mapping. Many machines can share a single `nixosConfiguration`, each receiving its hostname and network identity from DHCP. This has two compounding effects:

- **Build deduplication**: One `nixosConfiguration` means one build, regardless of how many machines consume it. Deploying 50 identical machines costs 1 build, not 50.
- **Parallel bootstrap**: All 50 machines can be bootstrapped simultaneously from the same configuration, since none of them need machine-specific NixOS config written first.

The machine's role in Panix is purely operational: it holds the SSH connection, the target address, and the transfer and activation state. The configuration is the blueprint; the machine is where it lands.

## How Inheritance Works

- **Tags**: Every name (flake, configuration, machine) is automatically a tag. Tags accumulate through the hierarchy.
- **Secrets**: Secrets defined at fleet/flake/configuration levels append down to machines. They are never replaced, only accumulated.
- **SSH**: Settings cascade down. A machine can override any SSH parameter.
- **Bootstrap**: Settings cascade down. Hooks at each level are collected.
- **Nix flags**: `extra_flags`, `build_flags`, `copy_flags` accumulate through inheritance.

## Disabling Parts of the Configuration

You can disable flakes, configurations, or machines by setting `disabled: true`:

```yaml
fleet:
  flakes:
    my-flake:
      disabled: true  # This flake and all its children are skipped
```

Disabled sections are filtered out during evaluation and do not participate in any phase.

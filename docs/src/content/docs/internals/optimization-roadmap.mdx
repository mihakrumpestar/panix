This article walks through the performance optimization journey of Panix. What started as investigating slow TUI rendering turned into a four-month deep dive that reduced CPU usage by 97% and memory allocations by 99%.

## The beginning (naive approach)

We had a working TUI built on [Bubble Tea](https://github.com/charmbracelet/bubbletea). It was fine at first, but with the introduction of e2e tests it became obvious that Panix's single thread was maxing out and making the TUI unresponsive.

It was obvious, that the renderer was doing far too much work. Every frame, every component: stats table, footer, viewports, phase status, build logs, was re-rendered from scratch, even when nothing had changed.

---

## Phase 1: Basic Caching

The initial solution was hash-based caching: compute an FNV hash of each component's content, skip the render when the hash matches the previous frame. The stats table alone saw a **96.7% CPU reduction**. Then we applied the same pattern to the footer, viewports, phase status, and build logs. The trade-off was minor: animated spinners in the stats table had to go, since they require constant re-rendering by definition.

The key insight from this phase was simple: the app was spending over 90% of its CPU time on TUI, re-rendering content that hadn't changed. Caching would fix that almost entirely.

---

## Phase 2: Optimized Bubble Tea Components

With caching in place, the next target was the components themselves. The viewport got improved cache hits by tracking whether only appended content changed. The tree renderer was rebuilt with node reuse based on xpath. A custom `tui.style` package replaced Bubble Tea's string-heavy styling with pre-rendered ANSI sequences. Benchmarks were added for all TUI packages to measure progress.

These were meaningful improvements, but they were optimizations on top of a framework that re-renders entire views every frame. CPU dropped to 11% and allocations to 4.4 GB, but it was clear that the framework itself was the ceiling.

---

## Phase 3: Initial zeroterm

The major change was building a custom TUI rendering engine from scratch ([PR #2](https://github.com/mihakrumpestar/panix/pull/2)). This was the single most impactful decision in the entire optimization effort.

`zeroterm` was built because Bubble Tea, despite being an excellent framework, re-renders entire views every frame with no built-in support for incremental rendering and using `string`s as an intermediate in all operations. Bubble Tea has to split, combine, append or cut strings at almost every step, making it a heavy burden on the Go garbage collector. For a deployment tool that monitors dozens of machines simultaneously and updates in real time, this meant the renderer was doing O(n) work every frame even when only a single line changed.

The entire `pkg/tui/` and `pkg/buffer/` packages were built from scratch: a contiguous line buffer (`LinesBuf`) for zero-copy line access, double-buffered frame diffing via `bytes.Equal` for zero-allocation change detection, pooled buffers via `sync.Pool`, pre-rendered ANSI prefixes and padding, and retained-mode components with incremental caching. CPU dropped from 11% to 2.6%, and allocations fell from 4.4 GB to 433 MB.

---

## Phase 4: Final

With the zeroterm architecture in place, the final phase was about rewriting the components built on top of it to fully leverage zero-allocation patterns.

[PR #7](https://github.com/mihakrumpestar/panix/pull/7) rewrote the viewport (scrollable content buffer, horizontal border cache), rebuilt the tree renderer, and optimized the style system. [PR #9](https://github.com/mihakrumpestar/panix/pull/9) rewrote build_logs to use the contiguous buffer directly, added a `stringbyte` package for zero-allocation string/byte conversions, optimized `atomicslice`, and improved xpath caching. The stats table and phase flow components were also reworked to minimize per-frame allocations.

These changes brought allocations from 433 MB down to 44 MB and CPU to 1.6%.

---

## Lessons Learned

- **Measure before you optimize.** Without building a benchmark, we would have been guessing. Several times, an "optimization" turned out to make things worse, and the benchmarks caught it immediately.
- **Caching is the biggest lever.** Most TUI components don't change between frames, and detecting that is cheap.
- **Allocations compound.** No single allocation was the problem. But when every component allocates on every frame, and you're rendering 60 times per second with dozens of log outputs, it adds up to gigabytes. Eliminating allocations one type at a time: pooled buffers, callback iteration, pre-computed values, eventually brought total allocations from 17.6 GB down to 44 MB.
- **Sometimes you need to build your own.** Bubble Tea is a good framework (altho is still lacking certain features like other frameworks (like build-in scrollbars)), but it wasn't designed for the kind of high-frequency, incremental rendering that Panix needed. Building a custom engine was a significant investment, but more than 200x performance improvement justified it.
- **Cache invalidation is hard.** One mistake, and cache won't work, or may produce visual artifacts due to being stale or improperly reused.

This article walks through the performance optimization journey of Panix. What started as investigating slow TUI rendering turned into a four-month deep dive that reduced CPU usage by 97% and memory allocations by 99.6%.

## Phase 1: Baseline

We had a working TUI built on [Bubbletea](https://github.com/charmbracelet/bubbletea), but profiling showed that the renderer was doing far too much work. Every frame, every component: stats table, footer, viewports, phase status, build logs, was re-rendered from scratch, even when nothing had changed. It was fine at first, but with the introduction of e2e tests it became obvious that Panix's single thread was maxing out and making the TUI unresponsive.

The initial solution was hash-based caching: compute an FNV hash of each component's content, skip the render when the hash matches the previous frame. The stats table alone saw a **96.7% CPU reduction**. Then we applied the same pattern to the footer, viewports, phase status, and build logs. The trade-off was minor: animated spinners in the stats table had to go, since they require constant re-rendering by definition.

The key insight from this phase was simple: the app was spending over 90% of its CPU time on TUI, re-rendering content that hadn't changed. Caching would fix that almost entirely.

---

## Phase 2: Intermediate

The previous phase showed the potential of caching, but it was clear that building around existing TUI frameworks would largely solve the performance problem, but never eliminate it. So the major change was building a custom TUI rendering engine from scratch (PR #2). This was the single most impactful decision in the entire optimization effort.

`zeroterm` was built because Bubbletea, despite being an excellent framework, re-renders entire views every frame with no built-in support for incremental rendering and using `string`s as an intermediate in all operations. Bubbletea has to split, combine, append or cut strings at almost every step, making it a heavy burden on the Go garbage collector. For a deployment tool that monitors dozens of machines simultaneously and updates in real time, this meant the renderer was doing O(n) work every frame even when only a single line changed.

The result is a rendering engine that's **166x faster** when updating every frame, **282x faster** when nothing changed, and **266x faster** for partial updates, compared to Bubbletea. See [Custom TUI Engine](/internals/tui-engine) for architecture details and benchmarks.

## Phase 3: Final

With the architecture in place, the final phase was about squeezing out the remaining allocations and CPU cycles from less optimized parts of the codebase.

Those were:

- Viewport optimizations (the scrollable content padded buffer and horizontal border cache).
- The tree renderer was rebuilt as a retained-mode component with node reuse based on xpath.
- XPath pre-computation and caching eliminated expensive string building from the hot path.
- Zero-allocation iteration replaced `Pairs()` with `ForEach()`, so that it no longer allocated pair slice on every call.
- Rate-limiting label update rate was a subtler fix (build log labels were updating at the full render rate (60fps) even though they only change with spinner state (8fps)).

Before these, the initial intermediate components and logic were already enumerated multiple times.

## Lessons Learned

- **Measure before you optimize.** Without building a benchmark, we would have been guessing. Several times, an "optimization" turned out to make things worse, and the benchmarks caught it immediately.
- **Caching is the biggest lever.** Most TUI components don't change between frames, and detecting that is cheap.
- **Allocations compound.** No single allocation was the problem. But when every component allocates on every frame, and you're rendering 60 times per second with dozens of log outputs, it adds up to gigabytes. Eliminating allocations one type at a time: pooled buffers, callback iteration, pre-computed values, eventually brought total allocations from 17.8 GB down to 76 MB.
- **Sometimes you need to build your own.** Bubbletea is a good framework (altho is still lacking certain features like other frameworks (like build-in scrollbars)), but it wasn't designed for the kind of high-frequency, incremental rendering that Panix needed. Building a custom engine was a significant investment, but more than 100x performance improvement justified it.
- **Cache invalidation is hard.**
